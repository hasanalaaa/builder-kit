# Migrations and queries

## 1. Migration rules

- One migration per logical change, generated by the project's tool (Supabase CLI, Drizzle Kit, Prisma Migrate, Alembic, Django) and committed.
- Never edit or delete a migration that ran on a shared environment. Write a new one.
- Review the generated SQL, not just the ORM diff. ORMs generate destructive SQL for renames.
- Run against a copy of production-shaped data before production. Time it.
- Backup / PITR confirmed before destructive steps.

## 2. Zero-downtime: expand → migrate → contract

Deploys overlap: old code and new code run at the same time against the same database. Every migration must work with both.

| Change | Safe sequence |
|--------|---------------|
| Add column | Add nullable (or with a constant default) → deploy code that writes it → backfill in batches → add NOT NULL (`NOT VALID` check then `VALIDATE`) |
| Rename column | Add new column → dual-write → backfill → switch reads → stop writing old → drop old (later release) |
| Change type | New column with new type → dual-write → backfill → switch → drop old |
| Drop column | Stop reading/writing in code → deploy → drop in a later migration |
| Drop table | Same as column; archive data first if retention requires |
| Add FK | `ADD CONSTRAINT ... NOT VALID` → `VALIDATE CONSTRAINT` (no long lock) |
| Add index (large table) | `CREATE INDEX CONCURRENTLY` (outside a transaction) |
| Add NOT NULL | `CHECK (col is not null) NOT VALID` → validate → `SET NOT NULL` (Postgres 12+ uses the check) |
| Split table | New table → dual-write → backfill → switch reads → drop old fields |

Backfills: batches of 1k–10k rows by primary key, with a pause, idempotent, resumable, logged. Never one `UPDATE` over millions of rows.

Locking hazards (Postgres): `ALTER TABLE` takes an ACCESS EXCLUSIVE lock; with a long-running query in front it queues and blocks everything behind it. Set `lock_timeout` (e.g. `set lock_timeout = '5s'`) in migrations and retry.

## 3. Indexes

- Index FKs, columns in WHERE/JOIN/ORDER BY of frequent queries.
- Composite: equality columns first, then range/sort: `(org_id, status, created_at desc)` serves `where org_id=? and status=? order by created_at desc`.
- Partial indexes for hot subsets: `where deleted_at is null`, `where status = 'open'`.
- Expression indexes for functions in filters: `(lower(email))`.
- Covering (`INCLUDE`) for index-only scans of hot queries.
- Don't index everything: each index slows writes and costs storage. Drop unused ones (`pg_stat_user_indexes.idx_scan = 0`).

## 4. Query patterns

**N+1**: loading a list then querying per row. Fix with a join, `IN (...)` batch, ORM eager loading (`include`, `with`, `selectinload`, `select_related/prefetch_related`), or a DataLoader in GraphQL. Detect: count queries per request in dev logs/tests.

**Pagination**:
- Offset (`LIMIT/OFFSET`) is fine for small tables and admin UIs; slow on deep pages.
- Keyset/cursor for feeds and large lists: `where (created_at, id) < ($1, $2) order by created_at desc, id desc limit 20`. Return an opaque cursor.
- Always cap `limit` server-side (e.g. max 100) — launch-security H7.

**Select only what you need**: no `select *` in hot paths; never return internal columns to clients.

**Transactions**: group writes that must succeed together (order + items + stock). Keep them short; no network calls inside.

**Concurrency** (launch-security H6):
- Counters/credits: atomic `update ... set balance = balance - $1 where id = $2 and balance >= $1 returning balance`.
- Uniqueness races: rely on unique constraints + `on conflict`.
- Lost updates: optimistic version check.
- Queues/jobs: `select ... for update skip locked`.

**Caching**: cache derived reads (dashboard aggregates) with explicit invalidation or short TTL; never cache per-user data under a shared key.

**Aggregates at scale**: materialized views refreshed on schedule, or summary tables updated by triggers/jobs.

## 5. ORM notes

- Prisma: use `@@index` for FKs and query columns; `Decimal` for money (or Int cents); `DateTime` maps to `timestamp(3)` by default — use `@db.Timestamptz(3)`.
- Drizzle: `timestamp(..., { withTimezone: true })`, `numeric` or `bigint` for money, define indexes in the table callback.
- SQLAlchemy: `DateTime(timezone=True)`, `Numeric(19, 4)`, Alembic autogenerate then hand-review.
- Django: `USE_TZ = True`, `DecimalField`, `select_related`/`prefetch_related`, `bulk_create`, `F()` expressions for atomic updates.

## 6. Backups and data lifecycle

- PITR enabled (Supabase Pro, Neon, RDS). Daily logical backup to separate storage for disaster recovery.
- Quarterly restore drill to a scratch database; record time to restore.
- Retention policy per table (logs 30–90 days, deleted accounts purged within the legal window).
- Seed scripts for dev/test that never contain real personal data.
- Test data factories in tests; anonymized production snapshots only with approval.
